# The feedback loop: local first, proofs on GitHub

The fast checks run on nezopt, in the local `lagent` pipeline. GitHub runs only the Verus proofs ([VERUS.md](VERUS.md)). There is no Rust job on GitHub for this repository: fmt, Clippy and tests run here.

| Tier | Runs | Where | Decides |
| --- | --- | --- | --- |
| Fast check | `scripts/check-fast` | Your worktree, before a commit | Nothing by itself; it tells you early |
| Lane result | `lane review-run` | Automatic, when a lane finishes | Nothing: it queues the result for a reviewer |
| Merge gates | `.lucina/pipeline.toml` | `lagent merge` | Whether the change lands |
| Proofs | `.github/workflows/verus.yml` | GitHub | `verus-gate`, read by the merge gate |

## `scripts/check-fast`

Run it before you commit. It checks only what the change touched, against `--base` (use `origin/main`: the local `main` ref of the main checkout can be stale):

- `diffgate`; rustfmt and Clippy on the touched files; the unit tests (`--lib`) of the touched workspace crates; standalone crates (their own `Cargo.toml` outside the workspace) through `--manifest-path`
- `shellcheck` on changed shell scripts, `actionlint` on changed workflows, `gitleaks` on the changed files, each only when installed
- the proof inventory (`lucina-ci inventory --check`). The Verus proofs the change reaches run on GitHub; `--proofs` runs them here (`--mutants` adds their mutants, `--all-proofs` lifts the limit of 12). It never waits on `/tmp/lucina-verify.lock`; if the lock is busy it says so

A missing tool or a skipped step is printed as skipped, never counted as passed. Older rustfmt and Clippy findings in files you did not touch do not fail the loop; findings in a file you touched do, even if they are old.

With `--merge-gate` the `diffgate` step honours the lead's waivers: it reads `LAGENT_ALLOW`, the entries of `lagent merge --allow RULE=reason`, and passes each one that is not one of lagent's own rules (`gate-change`, `spec-change`) to diffgate as `--allow RULE=reason` — a rule the list below marks `counted` excepted, whose entry must read `RULE=N:reason` or the step fails — printing every waiver it takes as `waived: <rule> = <reason>` and counting them on the step's line. Without `--merge-gate` the variable is ignored and the step says so, so neither a worker nor a lane verify step can waive diffgate for itself; an entry that is not `RULE=reason` fails the step and is named.

**The job's waivers file.** `lagent merge --allow RULE=reason` also writes every allow of the job to `<job dir>/waivers.jsonl` — one JSON object per line with exactly the four string fields `rule`, `reason`, `by`, `job` — and names that file in `LAGENT_WAIVERS_FILE` for its gate commands (`crates/lucina-agentd/src/pipeline/repo.rs` `waiver_lines`, LA-C014); it is set only when the job was given at least one allow, so an ordinary run of the fast check reads nothing and its `diffgate` step is the plain command it always was. The step of `check-fast --merge-gate` reads it and forwards each waiver whose rule the repository lists as `--allow RULE=reason` with the reason unchanged (so diffgate's counted form `RULE=N:reason` reaches it byte for byte), prints one line `diffgate waivers: N forwarded (…), M not forwarded (…)`, and FAILS the step — waiving nothing, never skipping — when the file cannot be read exactly: an unreadable or empty file, a line that is not JSON, a missing, repeated or fifth field, a non-string value, a blank reason each name the file, the line and the field (finding GATE-01: job_4ee819df2427 was allowed at the merge and its own diffgate pass then refused those very lines with "5 refusal(s), 0 waived"); a rule `LAGENT_ALLOW` already handed over travels once, because diffgate answers a waiver with the refusals the earlier entry left and calls the copy of it a failed waiver. Which rules may travel is data, not a constant: `tools/ci/merge-waiver-rules.txt` holds one rule name per line, `#` comments allowed, `skipped-test` and `tmp-write` today, a waiver of a rule that is not listed stays with the merge tool and is counted as not forwarded — `gate-change` and `spec-change` among them, because diffgate knows no such rule and forwarding one would fail the whole call with `--allow: unknown rule` — a list this step cannot read forwards nothing, adding a line there is a gate change a reviewer reads, and outside `--merge-gate` the file is ignored exactly like the variable (tests: `tools/ci/lucina-ci/tests/merge_gate_waivers.rs`). A rule name may carry one marker, `counted`: then its waivers travel only in diffgate's counted form `N:reason` and an uncounted one fails the step with `diffgate waivers: <rule> is forwarded in counted form only: write --allow <rule>=N:<reason> with N the exact number of refusals`, diffgate never run with the entries this form did like; `tmp-write` is marked so by the coordinator's allow of 2026-11-18 (LA-C013), `merge waivers: tmp-write may be forwarded, counted form only, for test lines that name /tmp on purpose`, and a word after the rule name that is not `counted` is a marker this step cannot read: it names the line and fails the step rather than read it as no marker.

Every step runs in a capped scope: 8 GiB, 4 CPUs, at most 256 tasks, its own time limit. All worktrees share one Cargo target, `~/.cache/lucina-check-target` (the one LucinaOS uses), so the loop adds no large target directory, and it refuses to build with under 20 GiB free. The launcher `tools/ci/lucina-ci` builds apart, in the small `~/.cache/secretary-ci-tool-build`, and reaches `~/.cache/secretary-ci-tool/release/lucina-ci` only through a `rename(2)`, because LucinaOS's launcher has the same package name. **A run keeps the tool it started with**: at its start `check-fast` copies that installed binary into a directory of its own (`$TMPDIR/check-fast-<pid>`, which goes with the run however it ended — GATE-07) and starts every step from the copy, so a rebuild by another `check-fast` or by a branch landing at the merge — even one that removes the shared name — cannot take the tool away from a run in flight (GATE-06: `Failed to find executable .../release/lucina-ci (deleted)`, merge job job_fc4fabf8e6fe, four steps lost 0.1 s after `clippy`; tests: `tools/ci/lucina-ci/tests/check_fast_tool_swap.rs`). A run is one job of the build queue (HOST-11): `scripts/check-fast` re-runs itself through `bq run --class long` (priority `gate` with `--merge-gate`, `--max-wait 3600`) unless it is already inside a bq job (`BQ_SLOT` set and `BQ_SLOT_PID` a live ancestor of the shell, nothing else), runs directly with `check-fast: no bq on this host; running without the queue` as its first line on stderr where there is no `bq` of ours, and each step scope it starts is placed in `build.slice` (tests: `scripts/tests/check-fast-queue-test.sh`, `tools/ci/lucina-ci/tests/check_fast_queue.rs`).

Measured on nezopt, 2026-11-10, on this CI change (25 files, the launcher crate, scripts and workflow): 24 s, 8 steps passed, the 55 reachable proofs left to GitHub.

## In `lagent merge`

Besides diffgate and `cargo check --workspace`:

- **proofs green on GitHub** (`scripts/gate-github-checks.sh`): a branch that reaches a proof unit needs `verus-gate` = `success` on its exact commit. Push the branch first (`git push origin <branch>`). See [VERUS.md](VERUS.md).
- **fast local check** (`scripts/check-fast --base HEAD^1 --merge-gate`): every step has its own time limit, counted from the moment the step runs, after `scripts/check-fast` has its queue slot — **180 s by default**, and `MERGE_STEP_LIMITS` in `tools/ci/lucina-ci/src/main.rs` names the steps that need more: `clippy` 240 s, `unit-tests-build` 1200 s and `unit-tests` 240 s, from the week of merges 2026-11-11..17 on nezopt (finding GATE-02, read-only in `/home/nez/scratch/proof-workflow/gate-02-step-times.md` §3, §5, §6): measured p95 151.6 s and 154.5 s over 27 and 23 completed runs, slowest clean run 162.2 s and 179.9 s, 15 of the week's 16 SecretaryIOS kills at the cap on these two steps, and all 50 completed runs of both under 240 s. **The tests are two steps since finding GATE-08** (merge job job_24cf4973dd74): one `cargo test` builds and links the test binaries of the touched crates before it runs a single one of them, and that build was the wait — JD-C018 measured `cargo test` for `lucina-server` (~50 test binaries) at 8 m 45 s under a 1-minute load of 24.59 with 40 s of tests in it (`/home/nez/scratch/platform-tools/jd-c018-tests.log`), and the step is what `lucina-server`, a root workspace member, merges on, which is how three merges (JD-C018, LM-C008, CO-C003) failed or waited on it, JD-C018 three times. So `unit-tests-build` runs `cargo test --no-run` with 1200 s of its own and 1200 s at the gate, because a slow build is not a test failure and the room has to be somewhere, and `unit-tests` runs the same command without it — same crates, same flags, same shared target — timed alone at the 240 s the measured week asked for (coordinator allow 2026-11-18, GATE-08). **A limit is set from measured p95 with headroom — `ceil(p95 x 1.5)`, rounded up to the next 30 s — and only ever raised by that rule**: where measurement does not argue for more, the number stays as it is, so a raise is a decision about a percentile and not about a merge that happened to fail. A limit only ever cuts: a step is never lifted above its own timeout, so `clippy` and `unit-tests` (each built with 300 s) really run 240 s at the gate, `unit-tests-build` runs its 1200 s because its own timeout was set to match it, and a step of its own 60 s, `fmt` or `diffgate`, keeps printing 60 whatever the table or the override says. At the gate each step's line prints the limit it ran under beside its measured time — `ok   clippy   97.3s / 240s` — and a step that used more than 80% of its limit (`MERGE_NEAR_LIMIT_SHARE`) adds `near-limit`, so the next review of a number starts from a log line instead of an audit. A step past its limit still FAILS the merge (`<step>: past its N s limit at merge: the machine is loaded; retry when it is quieter, or run scripts/check-fast in the worktree`, with that step's own N) and is never reported as skipped (2026-11-12: unit-tests were skipped at the merge gate under load and the merge went through with `0 failed`, job_b6094541ca4c); the two halves of the split are said in their own words, since GATE-08 — a build out of its time is `<step>: build too slow at load <1-minute load average>: not a test verdict` (it fails the merge just the same, so nothing lands unbuilt), and a run cut at its limit adds the tests it was in the middle of, read off its own log as `at the cut: <test>` lines, so a hang names itself. `LUCINA_CHECK_FAST_MERGE_CAP_S` overrides the whole table: one plain number is the limit of every step, and `step=SECONDS` entries separated by commas give one step its own; the tests use it rather than sleep a real 180 s, and nobody uses it to get a merge through. Tests: `tools/ci/lucina-ci/tests/merge_gate_timeout.rs`, `tools/ci/lucina-ci/tests/merge_gate_step_limits.rs`, `tools/ci/lucina-ci/tests/merge_gate_unit_tests_split.rs`. All the other gates stay as they were.
- **deploy shell tests** (`sh scripts/check-deploy-sh.sh`, since 2026-11-17, when a change touches `deploy/`): every `deploy/**/test-*.sh` in its own process. The shell scripts under `deploy/` have no Rust harness and check-fast only shellchecks them, so a watchdog rule that stopped watching anything used to merge green. Each test is hermetic: a stub `systemctl`/`curl` first on PATH, `HOME` and the XDG dirs in a scratch tree removed on exit, and no install, start, stop or restart. Run them the same way in a worktree: `sh scripts/check-deploy-sh.sh`.

## Delegated lanes

When a lane finishes successfully, `lane` (or `qcode-run` for Qwen) runs `lane review-run` detached: diffgate, then this repository's local check, and queues the result in `~/.local/state/lane-review/queue.jsonl`. It never merges or commits: a reviewer still reads each diff before `lagent merge`.

```bash
lane review
```

```bash
lane review --done <id>
```
